# Алгоритм FSM фиксации веса

Актуальная FSM работает по циклу «готовность → плато → запись → разгрузка → коррекция остатка».

## Настройки

Все параметры, влияющие на автоматическую запись, находятся в `SystemSettings` и доступны на странице **Настройки → Служба**:

- `MinWeight` — минимальная масса продукции;
- `ZeroResidualMaxKg` — единый максимум остатка для первой команды ZERO;
- `TareAllowancePercent` — допустимое превышение максимума ZERO для TARE;
- `PlateauStableSamples` — число стабильных измерений плато;
- `PlateauWindowKg` — допустимый разброс плато и стабильного остатка;
- `UnloadStableSamples` — число стабильных измерений для оценки остатка перед ZERO/TARE;
- `CommandTimeoutMs` — тайм-аут одной команды ZERO/TARE;
- `ZeroCommandMaxAttempts` — максимум попыток ZERO, по умолчанию 10;
- `TareCommandMaxAttempts` — максимум попыток TARE, по умолчанию 5;
- `MaxAutomaticZeroApplications` — максимум успешных автоустановок ZERO до следующего подтверждённого груза, по умолчанию 3;
- `MaxAutomaticTareApplications` — максимум успешных автоустановок TARE до следующего подтверждённого груза, по умолчанию 2;
- `EnableNonBlockingCorrection` — разрешать запись валидных грузов при защёлкнутой технологической ошибке; красная индикация при этом не гаснет, а новые команды коррекции не отправляются.

Верхняя граница TARE вычисляется как:

```text
TareMaxKg = ZeroResidualMaxKg * (1 + TareAllowancePercent / 100)
```

Настройки применяются после перезапуска службы. Числовые поля страницы реализованы стандартными `RadzenNumeric` и `RadzenNumericRangeValidator` по [официальному примеру Numeric](https://blazor.radzen.com/numeric?tabs=constant&theme=material3) и [документации валидатора](https://blazor.radzen.com/docs/api/Radzen.Blazor.RadzenNumericRangeValidator). Значения `HystWeight`, `SemaphoreTimeMs`, `ScaleSettings.StableThreshold` и `ScaleSettings.UnstableThreshold` читаются из старых файлов для совместимости, но новая FSM их не использует.

## Фиксация плато

FSM принимает только свежие ответы терминала. Для накопления плато требуется установленный аппаратный признак стабильности; окно плато сбрасывается нестабильным измерением или выходом разброса за `PlateauWindowKg`.

После запуска или восстановления связи стабильный вес не ниже `MinWeight` сразу считается началом плато. Предварительное подтверждение нуля для такого груза не требуется.

После `PlateauStableSamples` измерений с массой не меньше `MinWeight`:

1. вычисляется медиана окна;
2. медиана округляется до `Division` терминала, с резервным шагом 0,01 кг;
3. цикл помечается записанным;
4. запись немедленно передаётся в БД;
5. FSM остаётся в `AwaitUnload`.

Ошибка БД журналируется, но автоматического повтора нет: это исключает дубль при неизвестном результате записи. Повтор той же массы разрешён после подтверждённой разгрузки и создаёт новую запись.

## Разгрузка и остаточная вода

В состоянии `AwaitUnload` разгрузка подтверждается двумя последовательными свежими показаниями в диапазоне от `-TareMaxKg` до `+TareMaxKg`. Аппаратный признак стабильности для этих двух показаний не требуется. Нестабильные показания подтверждают только факт разгрузки; коррекция ZERO/TARE по ним не выполняется до получения `UnloadStableSamples` обычных стабильных показаний остатка. Остаток после снятия туши не вычитается из уже записанной массы.

- положительный остаток до `ZeroResidualMaxKg` включительно: до `ZeroCommandMaxAttempts` команд ZERO; после исчерпания попыток — красная ошибка без перехода к TARE;
- положительный остаток выше `ZeroResidualMaxKg` и до `TareMaxKg` включительно: до `TareCommandMaxAttempts` команд TARE с измеренной массой;
- отрицательный остаток в допустимом диапазоне: до `ZeroCommandMaxAttempts` команд ZERO без перехода к TARE;
- больший по модулю остаток, в том числе после уже записанного взвешивания: защёлкивается красная ошибка, команды не отправляются;
- после успешной команды FSM подтверждает результат новым стабильным окном; если малый остаток появился снова, он заново проходит классификацию ZERO/TARE (например, если на платформу налили воду);
- после `MaxAutomaticZeroApplications` или `MaxAutomaticTareApplications` успешных применений следующая команда соответствующего вида не отправляется и защёлкивается красная ошибка.

Каждая повторная попытка разрешается только после нового окна из `UnloadStableSamples` стабильных показаний. Поэтому терминал не получает команды в тесном цикле. Счётчики успешных автоустановок сохраняются на непрерывных нулевых кадрах после команды и сбрасываются новым подтверждённым грузом либо снятием защёлкнутой ошибки стабильным нулём.

Технологическая ошибка не снимается кнопкой и не снимается появлением очередного груза. Автокоррекция останавливается до очистки платформы и стабильного нуля (при необходимости — после ручной команды обнуления на терминале). При включённом `EnableNonBlockingCorrection` валидный груз всё ещё может быть записан, но `HasLatchedProcessError` остаётся активным и красная индикация имеет приоритет. При выключенном флаге запись блокируется до нуля.

Тайм-аут или ошибка COM считаются потерей связи. После восстановления связи автофиксация продолжается; признак уже записанного цикла сохраняется, поэтому восстановление не создаёт повторную запись.

Если новый груз появился до подтверждения околонулевого результата после команды, ожидание подтверждения прекращается, а груз обрабатывается как обычное взвешивание. Это не считается отказом команды.

## Сигналы

Соответствие кодов Arduino не менялось:

- аппаратная авария — `RedOn`;
- потеря связи — `LinkOff`;
- очистка, исчерпание попыток или превышение лимита автоустановок — `RedOn` до стабильного нуля;
- готовность — `Idle`;
- подтверждённое и записанное плато до разгрузки — `Completed`;
- набор плато и подтверждение разгрузки — `Unstable`.

При защёлкнутой технологической ошибке `RedOn` имеет приоритет над штатными состояниями FSM, в том числе во время разрешённой неблокирующей записи следующего груза. После перезапуска Arduino текущий красный сигнал отправляется повторно.

## CRC

В этом хотфиксе расчёт и проверка CRC не изменялись. Запрос массы остаётся прежним проверенным кадром, CRC входящего ответа только вычитывается из порта. Существующий метод формирования управляющих команд оставлен без изменений.

## Локальная проверка

По правилам репозитория команды не запускаются в Codex. На ПК с .NET 8 выполнить:

```powershell
dotnet test .\Scalemon.CSTests\Scalemon.CSTests.csproj -c Release
dotnet build .\Scalemon.sln -c Release
```

Перед публикацией отдельно проверить на терминале 10 отказов ZERO, 5 отказов TARE, повторное появление малого остатка после успешной команды, превышение лимитов 3/2, остаток выше `TareMaxKg` после снятия груза, снятие красной ошибки очисткой/ручным нулём и запись валидного груза при активной красной ошибке.
