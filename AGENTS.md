# Agents.md

> Инструкция для ИИ‑агентов (Codex и др.), работающих с репозиториями проекта **Scalemonitoring / Scalemon**.
>
> Цель — чтобы агент без лишних уточнений делал корректные PR в нужные части решения и следовал единым правилам.

---

## 0) Упрощённый режим (для новичка)

Если вы только начинаете или используете облачный Codex **без установленного .NET 8**:

- **Не запускать тесты и сборку в Codex.** Агент не должен выполнять `dotnet test` / реальный запуск приложения. Вместо этого — **только правки кода** и статическая проверка на глаз.
- **Маленькие и понятные PR.** Один PR = одна правка. Пример: «Отключить шумные логи HttpClient».
- **Никаких Prod‑конфигов.** Разрешены только Dev‑конфиги и документация.
- **Radzen‑компоненты строго по документации.** Использовать только официальные примеры из Radzen и не изобретать своих паттернов.
- **В PR описывать, как запустить локально на ПК с .NET 8.** Пример команд — ниже в файле.

## 1) Контекст проекта

- **Язык / платформа:** C# / .NET 8 (Windows Service + Blazor Server UI).
- **Состав репозитория:**
  - `Scalemon.ServiceHost` — Windows-служба, запускающая фоновые задачи.
  - `Scalemon.ApiService` — отдельный сервис с API и эндпойнтами.
  - `Scalemon.WebApp` — Blazor Server UI (Radzen компоненты, авторизация с ролями Viewer/Editor/Admin).
  - `Scalemon.Common` — общие модели/интерфейсы/утилиты.
  - `Scalemon.SerialLink` — драйверы COM/RS‑232 и процессор весов (включает протоколы «Масса‑К», Protocol 100 V3 и др.).
  - `Scalemon.SignalBus` — управление внешними индикаторами/реле (Arduino/RS‑485/USB).
  - `Scalemon.SqlDataAccess` — доступ к SQL Server (минимальные зависимости, ретраи, очереди).
  - `Scalemon.FSM` — конечные автоматы состояний весов/операций.
  - (могут присутствовать мигрированные с VB проекты и legacy WinForms UI).
- **БД:** SQL Server Express.
- **Логирование:** на SQLite, создаются отдельные файлы логов по дням. Ошибки работы с SQLite пока не выделяются, но планируется запись таких ошибок в отдельный текстовый файл. Не добавлять шум от HttpClient по умолчанию.
- **Окружения:** Dev (локально), Test (вирт. машина), Prod (мини‑ПК на участке).

## 2) Миссия и приоритеты для агента

1. **Сохраняем работоспособность Prod.** Любые потенциально опасные изменения — только за фича‑флаги, конфиги, или в отключаемом виде.
2. **PR с узким скоупом.** Один PR = одна тема (например, «Оптимизация разбора Protocol100»).
3. **Чистота истории.** Автогенерируемые файлы и большие бинарники в PR не включать.
4. **Тесты — не запускать в Codex.** Если .NET 8 недоступен, агент лишь добавляет/корректирует тесты по шаблону, но **не пытается их выполнять**. Проверка — локально у разработчика.
5. **Минимум шума в логах.** Логи только по делу, уровни: Error/Warn/Info; Debug — по фиче‑флагу.

## 3) Ветки, релизы, CI/CD

- **Рабочая ветка:** в данный момент используется `Scale-monitoring/Codex/add-sqlite-authentication-service` — основная для текущей разработки. Все изменения выполняются через PR в эту ветку и затем объединяются сразу после проверки.
- **Процесс работы:**
  1. В Visual Studio активируется нужная ветка и выполняются задачи Codex.
  2. После каждой задачи создаётся PR, который сразу объединяется с этой же веткой.
  3. Изменения скачиваются в Visual Studio и тестируются локально.
  4. После исправлений повторяется цикл «PR → объединение → тест».
  5. Когда код работает локально, выполняется ручная публикация через меню Visual Studio.
  6. Содержимое папки `Publish` копируется вручную на виртуальную машину для тестирования, а затем — на мини‑ПК (Prod).
- **Версионирование:** пока не используется.
- **Инсталлятор:** отсутствует, публикация выполняется вручную копированием.
- **Тестирование:** автоматические тесты пока не применяются.

## 4) Что трогать, а что — нет

- **Можно изменять:** код C#, `.csproj`, конфиги образцов `appsettings.Development.json`, DI‑регистрации, FSM‑настройки, документацию.
- **Нельзя без задачи:** `appsettings.Production.json`, скрипты миграций Prod, WiX/инсталлятор, схемы БД в Prod.
- **Секреты:** никогда не писать в код/PR (строки подключения, пароли, ключи). Использовать переменные окружения или `UserSecrets`.

## 5) Стандарты кода и стиля

- **C# 12 / .NET 8**. Nullable enabled. `async`/`await` — строго по смыслу.
- **Форматирование:** по возможности `dotnet format` (в Codex — не исполнять, просто соблюдать стиль), `file-scoped namespaces`.
- **Логирование Serilog:** краткие сообщения, структурированные свойства (`{@obj}` ограниченно), без лишних повторов.
- **Именование:** папки/классы по назначению; публичные API — XML‑комментарии, Summary на русском.

## 6) Принципы архитектуры

- **Слабая связность:** через интерфейсы из `Scalemon.Common`.
- **IoC/DI:** минимальные конструкторы, регистрируется в `ServiceHost`/`WebApp`.
- **FSM:** хранить конфигурацию переходов явно, без «магии».
- **Serial/COM:** все операции — с таймаутами и отменой `CancellationToken`.
- **SQL:** пул подключений, ретраи для кратковременных сбоев, транзакции там, где нужно.

## 7) Как давать задания Codex (шаблоны промптов)

> Используй эти шаблоны при работе в облаке Codex, в IDE‑расширении или через CLI. В описании обязательно указывай, какие проекты затрагивать и критерии готовности.

### 7.1 Оптимизация частоты опроса Protocol 100 (SerialLink)

**Задача:**

- Разобрать `Scalemon.SerialLink` и увеличить стабильную частоту опроса (ориентир: 5–6× быстрее, чем старый драйвер),
- соблюдая протокол «Протокол 100 V3».

**Требования готовности:**

- Подготовить юнит‑тест(ы) как примеры (исполнять их будет разработчик локально).
- Логи без спама при потере связи: один «disconnected» на эпизод, восстановление — один «connected».
- Настраиваемая скорость (4800/19200/…)
- Без регрессий в `Scalemon.FSM`.

### 7.2 Радикально уменьшить шум HttpClient

**Задача:** отключить информационные логи HttpClient по умолчанию; оставить уровни `Warning+` или включать `Debug` только по конфиг‑флажку `Logging:HttpClient:Debug`.

### 7.3 Логи в SQLite (опциональный бэкенд для WebApp)

**Задача:** добавить провайдер логов SQLite для `Scalemon.WebApp` (только Dev/Test), с пагинацией без тормозов на файлах >100 МБ. **Критерии:** чтение логов на странице < 1 c при 100k+ записей; индексы по времени и уровню.

### 7.4 Добавить пользователя SQL (админ‑скрипт)

**Задача:** подготовить безопасный скрипт создания пользователя `ScalemonUser` для БД `WeighingDB` без вмешательства в Prod‑схему; снабдить инструкциями по применению.

### 7.5 Правила для страниц на Radzen (Blazor Server)

**Главное правило: придерживаться официальной документации Radzen.**

- Использовать компоненты и параметры так, как показано в примерах Radzen (DataGrid, Splitter, PanelMenu, DialogService и т.д.).
- Не плодить собственные «переизобретённые» компоненты, если уже есть стандартный Radzen‑аналог.
- Разметка читаемая: один компонент — одна ответственность, без чрезмерной вложенности.
- Стили — через параметры/классы Radzen; кастомный CSS только при необходимости и коротко.
- Навигация/State — стандартными средствами Blazor и Radzen (NavigationManager, Dialog/Notification).
- В PR добавлять ссылку на раздел(ы) документации Radzen, на которых основано решение.

## 8) Правила PR от агента

- **Название:** короткое, предметное. Пример: `feat(seriallink): faster Protocol100 parsing + stable reconnect`
- **Описание:**
  - «До/после», метрики (время, частота опроса, размер логов).
  - Список проектов/файлов, где были изменения.
  - Риски и план отката (toggle/конфиг/ветка).

## 9) Тестовые данные и режимы

- **Локальные профили конфигов:** `appsettings.Development.json` — можно править; `Production` — нельзя.

## 10) Ошибки и устойчивость

- **COM‑порт:**
  - открывать/закрывать безопасно; повторное открытие — допустимо;
  - таймауты чтения/записи заданы и конфигурируемы;
  - при потере связи: один лог «нет связи», без многократных записей.
- **FSM:** переход «подключено/отключено» фиксировать по порогам «хороших/плохих» кадров; не дергать «подключено»/«отключено» часто.
- **SQL:** при падении БД — выставлять флаг `_isDbDown`, очередь ретраев, события `DatabaseFailed`/`DatabaseRecovered`.

## 11) Документация кода

- Каждый публичный метод библиотек — XML‑комментарий с кратким описанием.
- Для протоколов/парсеров — ссылка на спецификацию и бинарные примеры фреймов (в комментарии).
- В README подсекция «Как воспроизвести проблему/тест».

## 12) Конвенции коммитов

Формат: `type(scope): subject`

- `feat`, `fix`, `perf`, `refactor`, `chore`, `docs`, `test`, `ci`.
- Максимум 72 символа в subject, описание — при необходимости.

## 13) Запросы на обсуждение (RFC)

Если изменение спорное (изменение БД/установщика/безопасности) — вместо PR открыть Issue с пометкой `rfc` и кратким предложением, вариантами и оценкой рисков.

## 14) Быстрый старт для агента (шаги)

1. Создать ветку `feature/<topic>` от последнего `main`/`develop` (или текущей рабочей ветки, если так удобнее).
2. **В Codex:** внести правки по задаче, не пытаясь запускать сборку/тесты. В PR указать, как запускать локально.
3. **Локально у разработчика:** обновить ветку, собрать и проверить минимальные сценарии в Visual Studio.
4. При необходимости повторить цикл «PR → объединение → локальная проверка».
5. Обновить документацию (`README`, этот файл при необходимости).
6. Ручная публикация через Visual Studio и копирование папки `Publish` на тест/Prod (как сейчас по процессу).

## 15) Локальные команды (памятка) (памятка)

```bash
# (Запускаются ЛОКАЛЬНО разработчиком, не в Codex)
# Сборка и форматирование

# Публикация службы
 dotnet publish Scalemon.ServiceHost -c Release -r win-x64 \
   /p:PublishSingleFile=true /p:PublishTrimmed=false

   /p:PublishSingleFile=true /p:PublishTrimmed=false
```
