# Установка, обновление и возврат Scalemon

## Состояние поставки

Исходники установщика NSIS, Updater, локальной утилиты обслуживания, административного интерфейса,
подписанных пакетов и тестов входят в решение. Сборка, запуск служб и тесты в Codex не выполняются
по AGENTS.md. До публикации Stable обязательна приёмка на отдельной Windows VM по таблице ниже.
Наличие исходников и успешная статическая проверка не означают, что выпуск уже принят для участка.

Ключ подписи не создаётся агентом и не поставляется с закрытой частью в репозитории.
Первый распространяемый Setup необходимо собрать с открытым ключом владельца выпуска.
Без встроенного ключа Updater отклоняет автоматическую доставку; режима обхода подписи нет.

## Компоненты и данные

- ServiceHost — одна Windows-служба с учётом, API и Blazor.
- Updater — самостоятельная Windows-служба `Scalemon.Updater`, выполняющая доставку и переключение.
- Maintenance — локальное окно администратора, доступное без работающего Blazor.
- NSIS — русскоязычный мастер новой установки, подключения существующей и повторной установки инфраструктуры.

Программа хранится в `%ProgramFiles%\Scalemon\Versions\<version>`.
Updater и Maintenance размещаются отдельно в `Infrastructure\Updater` и `Infrastructure\Maintenance`,
чтобы их зависимости не перезаписывали друг друга. Активный путь хранит SCM.
В `%ProgramData%\Scalemon` находятся `Config`, `Data`, `Logs`, `Updates`, `Backups`.
Контрольный файл `Updates\installation.json`, журнал и состояние Updater доступны основной службе
только для чтения. Настройки приложения в Config допускают сохранение из интерфейса.
Основная служба использует service SID; установщик сохраняет существующую учётную запись.
Updater имеет административные полномочия. Локальный протокол сверяет PID сервера с SCM,
разрешает только известные команды и не доступен по сети.

Папки версий содержат весь self-contained win-x64 publish, включая DLL, runtime и wwwroot.
Контрольный список проверяет все файлы резервной версии перед откатом. Файлы работающего комплекта
не заменяются. Хранятся текущая версия и одна предыдущая; при операции также существует кандидат.
Обновление Updater v1 выполняется Setup, а не автоматическим пакетом приложения.

## Первое подключение участка

1. Остановить работу участка, выключить весы и убедиться в сохранении записей. Старая версия до
   внедрения этого функционала не поддерживает программный барьер обслуживания; установщик запрашивает
   явное подтверждение остановки участка.
2. Запустить Setup от администратора. Мастер ищет существующую службу Scalemon; при нескольких
   экземплярах нужно проверить выбранное имя. SQL-поле можно оставить пустым для сохранения подключения.
3. Проверить COM-порты и порт веб-интерфейса. SQL Server и драйверы уже должны быть установлены.
   Для нового пользователя `admin` требуется пароль не менее 12 символов.
4. Исходная публикация и сведения о регистрации службы копируются в `Backups\setup-<UTC>`.
   Стандартные локальные данные переносятся при остановленной службе; SQLite копируется вместе с WAL/SHM.
   Пользовательские абсолютные пути сохраняются. SQL Server не переносится и его схема не изменяется.
5. Новая версия запускается в режиме проверки. Учёт закрыт до подтверждения доступа к SQL и локальным
   хранилищам от имени службы. Только после этого разрешается рабочий режим.

При неудаче настройки исходный комплект и снимки остаются в Backups. Ошибка остановки не приводит к
принудительному завершению процесса. При аварии во время самого первого перехода с legacy-версии
может потребоваться восстановить исходную регистрацию по `service.json`: legacy не умеет отвечать
на проверку нового Updater. Этот сценарий отдельно проверяется на VM до первого внедрения.

Повторный Setup того же номера восстанавливает инфраструктуру и проверяет неизменность комплекта
приложения. Повреждённые файлы действующей версии нельзя молча перезаписать тем же номером —
нужно диагностировать повреждение и использовать исправленный выпуск. Более старый Setup блокируется;
возврат программы выполняется через обслуживание.

## Обычная работа и отмена

Updater проверяет GitHub при запуске и раз в час. По умолчанию загружает Stable автоматически.
Для установки одновременно требуются ночное окно 22:00–05:00, десять минут актуальной телеметрии
«нет связи», отсутствие активных изменений и сохранение всех записей. После рестарта Updater
интервал наблюдения начинается заново. Остановленный процесс и устаревшая телеметрия не означают
выключенные весы. Восстановление связи до остановки отменяет подготовку.

Отключение питания весов и обрыв кабеля программно не различаются: ночное окно — дополнительное
ограничение, а не доказательство физического выключения. Не включать весы, пока интерфейс сообщает
о переключении версии.

На странице `/updates`, доступной только Admin, можно проверить выпуск, изменить канал и часы,
отменить ожидающую установку, выключить автоустановку и вернуть предыдущую версию.
Ручная установка и возврат допускаются вне ночного окна, но сохраняют проверки отключения и данных.
Отменённый или неудачный выпуск исключается из автоматики до явной команды установки.
Возврат приостанавливает автоустановку. Настройку можно включить заново после анализа причины.

После начала переключения отмена не прерывает замену регистрации службы. Исполнитель завершает
операцию либо возвращает предыдущий комплект. Accepted фиксируется до разрешения новых взвешиваний;
после этой точки поздняя ошибка очистки или связи не запускает автоматический откат.

Откат меняет программу, но не SQL, локальные базы и текущие настройки. Пакеты v1 обязаны быть
обратно совместимыми с форматом данных предыдущего выпуска. Необратимые миграции публикуются
отдельно, с ручной процедурой обслуживания, и не помечаются `backwardCompatible=true`.
Резервные снимки настроек в Backups предназначены для диагностики, а не автоматического отката данных.

Если кандидат и резервная версия не запускаются, автоматические попытки прекращаются. Через локальное
обслуживание можно повторить восстановление прерванной операции. После устранения причины и успешного
восстановления перезапустить `Scalemon.Updater` через службы Windows; не менять журнал вручную.
Данные переживают обычное удаление программы. Удаление требует того же безопасного барьера.

## Выпуск и подпись

Репозиторий публичный, токен GitHub на мини-ПК не нужен. Версия — SemVer в нижнем регистре, тег `vX.Y.Z`.
На сервере сборки нужны .NET SDK 8, PowerShell 7.4+ и NSIS 3.11. На участке PowerShell 7 и отдельный .NET
не требуются: программы публикуются self-contained.

Владелец один раз создаёт P-256 ключ за пределами репозитория, например:

```powershell
./installer/New-ReleaseSigningKey.ps1 -PrivateKeyPath D:\ReleaseKeys\Scalemon.private.pem -PublicKeyPath D:\ReleaseKeys\Scalemon.public.pem
```

Затем в GitHub создать Environment `release`, включить обязательного проверяющего и настроить:

- secret `RELEASE_SIGNING_KEY_PEM` — содержимое закрытого PEM;
- variable `RELEASE_PUBLIC_KEY_PEM` — соответствующий открытый PEM.

Ключ должен оставаться тем же между выпусками. В v1 смена корня доверия требует нового Setup.
Подпись формата IEEE P1363, ECDSA P-256/SHA-256 применяется к точным UTF-8 байтам манифеста.
Манифест содержит хеш, размеры, архитектуру, версию, Git SHA, канал и требования совместимости.
Первоначальный Setup не подписан Authenticode автоматически: такой сертификат не предоставлен.
Подпись обновлений не заменяет Authenticode-подпись EXE и не устраняет возможный запрос SmartScreen.

Workflow `Build Scalemon release` по тегу создаёт **черновик Test**, выполняет тесты в CI, собирает
программы и NSIS. Публикации Stable при merge в main нет. Выпуск без ключа завершается ошибкой.
Существующий релиз не перезаписывается повторной сборкой. В релиз входят только Setup, ZIP,
`release-manifest.json` и `release-manifest.sig`; рабочие данные и конфиги исключаются.

Чтобы Test-канал на VM увидел выпуск, после проверки состава файлов вручную опубликовать черновик как
prerelease. Это ещё не Stable. Не переводить выпуск в обычный release до завершения таблицы приёмки.

После приёмки Test на VM запустить `Promote tested Scalemon release`, указав тот же номер.
Сценарий проверяет подпись и SHA-256 ранее собранного архива, меняет только подписанные метаданные
канала и переводит prerelease в Stable. ZIP и Setup не пересобираются. Это единственное разрешённое
изменение метаданных при продвижении; повторная публикация другой программы под прежним номером запрещена.
Для prerelease-тестирования можно использовать обычный номер `1.0.1`, отметив GitHub Release как prerelease;
номер вида `1.0.1-rc.1` не продвигается в Stable этим сценарием.

Локальная сборка владельцем (не в Codex):

```powershell
dotnet build Scalemon.ServiceHost/Scalemon.ServiceHost.csproj -c Release
dotnet build Scalemon.Maintenance/Scalemon.Maintenance.csproj -c Release
dotnet build Scalemon.Updater/Scalemon.Updater.csproj -c Release
dotnet test Scalemon.CSTests/Scalemon.CSTests.csproj -c Release
dotnet test Scalemon.UpdateTests/Scalemon.UpdateTests.csproj -c Release
./installer/Publish-Release.ps1 -Version 1.0.0 -Channel Test -SigningKeyPath D:\ReleaseKeys\Scalemon.private.pem -PublicKeyPath D:\ReleaseKeys\Scalemon.public.pem -OutputDirectory D:\Releases\Scalemon-1.0.0 -Makensis 'C:\Program Files (x86)\NSIS\makensis.exe'
```

В текущем solution есть legacy C++/Arduino-конфигурации; для этих проверок используются отдельные C#
проекты. Установщик содержит только ServiceHost и инфраструктуру, не прошивку Arduino.

## API и статусы

`GET /api/updates` возвращает состояние. `GET /api/updates/token` выдаёт antiforgery-токен для
авторизованного администратора. `POST /api/updates` принимает только `check`, `install`, `rollback`,
`cancel`, `settings`; требуется токен в заголовке, имя которого возвращено token endpoint.
Для install нужен идентификатор доступной версии, а не URL или путь. Роль Admin проверяется сервером.
Blazor использует серверный авторизованный circuit и повторно проверяет роль перед каждой командой.

Локальный протокол ограничен 256 КБ, четырьмя соединениями и таймаутами. Updater не слушает TCP-порт.
Главная служба предоставляет локальные `status`, `prepare`, `resume`, `dependencies`.
`GET /health/ready` публикует только готовность процесса; состояние выключенных весов не является ошибкой
запуска. Браузер автоматически перезагружает потерянный Blazor circuit после восстановления службы.

## Приёмка на Windows VM

Работать только со снимком тестовой VM и копией данных, отдельно от мини-ПК участка.
Проверить на Windows 10 и Windows 11 x64. Сначала создать два подписанных тестовых выпуска A и B.
Для SQL использовать отдельную тестовую БД с существующей схемой проекта и учётными правами службы.
Для COM — подключённое тестовое оборудование либо заранее подготовленные виртуальные порты и эмулятор.

| Проверка | Критерий |
|---|---|
| Чистая установка без .NET | Служба, API, интерфейс и Maintenance запускаются |
| SQL/драйвер отсутствует | Ошибка с причиной; ложной готовности нет |
| Перенос legacy | Совпадают пользователи, настройки, режимы, проекты и количество записей |
| Повторный Setup | Нет дубликатов служб и сброса учётной записи |
| Ночь, весы подключены | Обновление не начинается |
| День, весы отключены | Пакет ожидает расписания |
| Короткий обрыв/перезапуск Updater | Десятиминутное наблюдение начинается заново |
| Потеря SQL с записью в очереди | Обновление запрещено до сохранения |
| Запись извлечена из очереди и выполняется | PendingWrites остаётся больше нуля |
| Активное распознавание/правка | Не возникает частично записанного проекта |
| Восстановление связи/отмена подготовки | Старая версия продолжает работу |
| Подмена манифеста/ключа/ZIP | Отказ до остановки службы |
| Нехватка диска/нет GitHub | Учёт текущей версии продолжается |
| A → B | Путь SCM указывает B; A сохранена полностью |
| Неисправный кандидат B | Возврат A; B исключена из автоматики |
| B → A вручную после новых записей | Новые данные остаются, автоматика приостановлена |
| Отключение питания на Prepared/Stopped/Switching/Validating/Accepted | Согласованная версия; Accepted не приводит к откату после новых данных |
| Не запускаются обе версии | Нет бесконечного цикла; диагностика и восстановление через Maintenance |
| Нет браузера/монитора/интерактивного входа | Обновление выполняется службами |
| Пользователь без Admin | Нет команд обновления через HTTP, circuit или pipe |
| Удаление | Нет службы и программных файлов; базы, настройки, сканы сохранены |

Для проверки отключения питания использовать управление VM на хосте и отслеживать `operation.json`;
не имитировать этот сценарий на производственном компьютере. Отдельно проверить начальный legacy-переход.
Результаты вписать в протокол VM: версии, Git SHA, Windows, дата, сценарий и фактический результат.
До заполнения этого протокола выпуск не переводится в Stable.

Radzen: [Button](https://blazor.radzen.com/button), [CheckBox](https://blazor.radzen.com/checkbox),
[Numeric](https://blazor.radzen.com/numeric). У компонентов использованы стандартные параметры и события.
